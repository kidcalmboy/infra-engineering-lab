# Day 2 - 텍스트 처리 개념 보강

이 문서는 `find`, `grep`, `wc`, 파이프, `sort`, `uniq`, `cut`, `awk`를 단순 명령어 암기보다 **Linux가 텍스트를 어떻게 흘려보내고 명령어들이 어떻게 역할을 나눠 처리하는지** 이해하기 위해 정리한 개념 보강 문서다.

## Linux 명령어를 연결해서 사용하는 이유

Linux CLI에서는 하나의 명령어가 모든 일을 하도록 만들기보다, 각 명령어가 비교적 명확한 역할을 수행하고 결과를 다른 명령어에 넘기는 방식이 많이 사용된다.

예:

```bash
grep "ERROR" server.log | wc -l
```

이 명령은 하나의 거대한 기능이 아니라 두 단계로 동작한다.

```text
server.log
   ↓
grep
ERROR가 포함된 줄만 출력
   ↓
파이프 |
   ↓
wc -l
전달받은 줄 수 계산
```

이런 식으로 작은 명령어들을 조합하면 로그 검색, 집계, 필터링을 유연하게 수행할 수 있다.

## 표준 입력과 표준 출력의 기본 개념

명령어를 이해할 때는 입력과 출력을 생각하면 쉽다.

```text
입력(Input)
→ 명령어가 처리
→ 출력(Output)
```

예를 들어:

```bash
cat server.log
```

은 파일 내용을 읽어 화면에 출력한다.

```bash
cat server.log | grep "ERROR"
```

에서는 `cat`의 출력이 화면으로 끝나는 대신 `grep`의 입력으로 전달된다.

즉 파이프는:

```text
왼쪽 명령의 표준 출력
→ 오른쪽 명령의 표준 입력
```

을 연결하는 역할을 한다.

앞으로 여러 명령어가 길게 연결돼 있어도 왼쪽부터 **각 단계가 어떤 데이터를 출력하는지** 따라가면 이해하기 쉽다.

## `find`와 `grep`은 검색 대상이 다르다

둘 다 '찾는다'는 느낌 때문에 헷갈리지만 검색하는 대상이 다르다.

```text
find
→ 파일시스템에서 파일/디렉터리 자체를 찾음

grep
→ 텍스트 내용에서 문자열/패턴을 찾음
```

예를 들어 `server.log`가 어디 있는지 모른다면:

```bash
find ~ -name "server.log"
```

파일 위치는 알고 있고 그 안에서 ERROR를 찾는다면:

```bash
grep "ERROR" server.log
```

운영 장애 상황에서는 다음처럼 연결해서 생각할 수 있다.

```text
로그 파일 위치를 모름
→ find

로그 파일 위치를 앎
→ grep으로 내용 확인
```

## `grep`은 줄 단위 필터라고 생각하면 쉽다

`grep`은 파일을 검색해서 단어 하나만 출력하는 것이 아니라, 기본적으로 **조건에 맞는 줄 전체를 출력**한다.

입력:

```text
INFO server started
ERROR database failed
INFO retry
```

실행:

```bash
grep "ERROR" server.log
```

출력:

```text
ERROR database failed
```

따라서 `grep`은 로그 분석에서 '필요한 줄만 다음 단계로 보내는 필터'처럼 사용할 수 있다.

```bash
grep "ERROR" server.log | wc -l
```

여기서 `grep`은 ERROR 줄만 남기고, `wc`가 그 결과를 계산한다.

## `wc -l`의 의미

`wc`는 Word Count 계열 명령어로 줄, 단어, 바이트 등의 수를 셀 수 있다.

이번 실습에서 사용한:

```bash
wc -l
```

의 `-l`은 **line count**, 즉 줄 수를 의미한다.

```bash
grep "ERROR" server.log | wc -l
```

은 실제 의미가:

```text
ERROR를 찾는다
→ 찾은 줄들을 전달한다
→ 전달된 줄이 몇 개인지 센다
```

이므로 ERROR 발생 건수를 빠르게 집계할 수 있다.

단, 같은 장애가 여러 줄의 로그를 남기는 프로그램이라면 '줄 수 = 장애 발생 횟수'가 항상 성립하는 것은 아니다. 로그 형식의 의미를 먼저 이해해야 한다.

## `sort`가 원본을 수정하지 않는 이유

```bash
sort level.log
```

은 파일을 정렬해서 **결과를 출력**할 뿐 원본 파일 순서를 바꾸지 않는다.

이는 `grep`, `awk`, 기본 `sed` 등 많은 Linux 텍스트 명령이 기본적으로:

```text
읽기
→ 처리
→ 결과 출력
```

방식을 사용하기 때문이다.

정렬 결과를 파일로 저장하려면:

```bash
sort level.log > sorted.log
```

처럼 출력 방향을 파일로 바꿔야 한다.

## `uniq`가 정렬과 함께 사용되는 이유

`uniq`에서 가장 중요한 개념은 **연속된 중복만 인식한다**는 점이다.

입력:

```text
ERROR
INFO
ERROR
```

여기서:

```bash
uniq
```

를 해도 두 ERROR는 떨어져 있으므로 하나로 합쳐지지 않는다.

먼저:

```bash
sort
```

하면:

```text
ERROR
ERROR
INFO
```

가 되고 그 다음:

```bash
uniq -c
```

를 적용하면:

```text
2 ERROR
1 INFO
```

로 정확하게 묶을 수 있다.

따라서 다음 패턴을 많이 사용한다.

```bash
sort | uniq -c | sort -nr
```

의미:

```text
같은 값끼리 모음
→ 각 값 개수 계산
→ 개수가 큰 순으로 정렬
```

## `sort -nr`의 `n`과 `r`

```text
-n
→ numeric, 문자열이 아니라 숫자 값으로 비교

-r
→ reverse, 큰 값부터 역순 출력
```

`uniq -c`의 결과는 앞쪽에 숫자가 붙기 때문에:

```bash
sort -nr
```

를 사용하면 발생 횟수가 많은 항목부터 볼 수 있다.

로그 분석에서는 '가장 많이 발생한 에러/IP/서버'를 빠르게 확인할 때 유용하다.

## `cut`의 핵심은 구분자와 필드

한 줄이 다음과 같다고 하자.

```text
alice:web:200
```

`:`를 기준으로 보면:

```text
1번 필드 = alice
2번 필드 = web
3번 필드 = 200
```

따라서:

```bash
cut -d ':' -f 2
```

의 의미는:

```text
-d ':'
→ : 문자를 필드 구분자로 사용

-f 2
→ 두 번째 필드만 출력
```

이다.

`cut`은 구조가 단순하고 구분자가 명확한 텍스트에서 필요한 열만 빠르게 뽑을 때 적합하다.

## 왜 보통 `cut → sort → uniq` 순서로 쓰는가

예:

```text
web01:ERROR
web02:INFO
web01:ERROR
```

서버 이름별 개수를 알고 싶다면 먼저 필요한 정보인 서버 이름만 뽑는다.

```bash
cut -d ':' -f 1 problem03.log
```

결과:

```text
web01
web02
web01
```

이제 같은 값끼리 붙이고:

```bash
sort
```

개수를 센다.

```bash
uniq -c
```

즉:

```text
필요한 데이터 추출
→ 그룹화가 가능하도록 정렬
→ 집계
```

순서다.

이런 데이터 흐름을 생각하면 긴 파이프 명령도 외우지 않고 만들 수 있다.

## `awk`는 줄을 '필드들의 집합'으로 본다

`awk`의 핵심은 텍스트 한 줄을 여러 필드로 나눠 처리하는 것이다.

예:

```text
10.0.0.1 GET /index.html 200 120
```

기본 공백 구분 기준:

```text
$1 = 10.0.0.1
$2 = GET
$3 = /index.html
$4 = 200
$5 = 120
```

전체 줄은:

```text
$0
```

로 표현할 수 있다.

즉 `awk`에서는:

```text
$0 = 한 줄 전체
$1 = 첫 번째 필드
$2 = 두 번째 필드
...
```

라고 생각하면 된다.

## `awk '조건 {동작}'`의 의미

예:

```bash
awk '$4 >= 400 {print $1, $3}' access.log
```

을 나누면:

```text
$4 >= 400
→ 네 번째 필드가 400 이상인 줄만 선택

{print $1, $3}
→ 선택된 줄에서 첫 번째와 세 번째 필드 출력
```

따라서 `awk`는:

```text
어떤 줄을 고를지
+
그 줄에서 무엇을 출력/계산할지
```

를 동시에 표현할 수 있다.

이 점이 단순 필드 추출 중심인 `cut`과의 가장 큰 차이다.

## `cut`과 `awk` 선택 기준

```text
단순히 : 기준 두 번째 값만 필요
→ cut

상태코드가 400 이상인 줄에서 IP만 필요
→ awk

여러 조건을 조합하거나 계산 필요
→ awk
```

명령어를 많이 쓰는 것이 좋은 것이 아니라 **가장 단순하게 문제를 해결할 수 있는 도구를 선택하는 것**이 중요하다.

## 파이프라인을 읽는 방법

다음 명령을 보자.

```bash
grep "ERROR" problem03.log | cut -d ':' -f 1 | sort | uniq -c | sort -nr
```

통째로 외우지 말고 왼쪽부터 해석한다.

```text
1. grep "ERROR"
   → ERROR 줄만 남김

2. cut -d ':' -f 1
   → 서버 이름만 추출

3. sort
   → 같은 서버끼리 붙임

4. uniq -c
   → 서버별 ERROR 개수 계산

5. sort -nr
   → ERROR가 많은 서버부터 정렬
```

즉 최종 질문은:

```text
어떤 서버에서 ERROR가 가장 많이 발생했는가?
```

가 된다.

이처럼 파이프라인은 **질문을 작은 처리 단계로 나눈 것**이라고 생각하면 된다.

## 운영 Troubleshooting에 적용하는 사고방식

로그 장애 분석은 바로 복잡한 명령을 쓰기보다 다음처럼 단계적으로 접근한다.

```text
1. 로그 위치 확인
2. 실제 오류 내용 확인
3. 필요한 조건만 필터링
4. 필요한 필드 추출
5. 발생 건수/패턴 집계
6. 결과 해석
```

예를 들어:

```bash
grep "ERROR" server.log
```

으로 먼저 실제 오류 메시지를 본 뒤:

```bash
grep "ERROR" server.log | wc -l
```

로 건수를 세는 이유도 같다.

처음부터 숫자만 보면 어떤 오류인지 모르기 때문에 **내용 확인이 먼저이고 집계는 그 다음**이다.

## 핵심 정리

```text
find
→ 파일/디렉터리 자체 검색

grep
→ 조건에 맞는 텍스트 줄 필터링

|
→ 왼쪽 명령의 출력을 오른쪽 명령의 입력으로 연결

wc -l
→ 줄 수 계산

sort
→ 정렬, 원본 파일은 기본적으로 수정하지 않음

uniq
→ 연속된 동일 값 처리

uniq -c
→ 연속된 동일 값의 개수 계산

cut
→ 구분자 기준 단순 필드 추출

awk
→ 필드 기반 조건 처리, 출력, 계산
```

가장 중요한 개념은 개별 명령어 암기보다 다음이다.

```text
입력
→ 필터링
→ 필요한 정보 추출
→ 정렬/집계
→ 결과 해석
```

이 흐름을 이해하면 새로운 로그 형식을 만나도 기존 명령어들을 조합해서 분석할 수 있다.
